# mbusgw-t2r --- Руководство пользователя (русский)

*Шлюз MODBUS TCP в RTU. Руководство написано «для маленьких»: каждый шаг расписан, ничего не
подразумевается. Английская версия --- в файле `UserGuide_EN.md`.*

---

## 1. Что делает эта программа

У вас есть устройство (счётчик электроэнергии, терморегулятор, ПЛК...), которое говорит на
**MODBUS RTU** по последовательной линии (RS-485 или RS-232). И есть программа на компьютере
или в сети (SCADA, скрипт, `mbpoll`...), которая говорит на **MODBUS TCP** по сети.

Шлюз стоит между ними и переводит:

```
 [Ваш TCP-клиент] --- сеть TCP/IP ---> [mbusgw-t2r] --- последовательная линия ---> [RTU-устройство]
     (SCADA,                           (эта программа)      (RS-485/RS-232)          (счётчик, ПЛК...)
      mbpoll, ...)
```

- Несколько TCP-клиентов могут подключаться одновременно --- шлюз выстраивает их в очередь,
  чтобы на линию уходил только один запрос за раз (линия RTU физически не умеет два сразу).
- На одной линии RS-485 может сидеть несколько устройств --- они различаются *адресом
  ведомого* внутри самого MODBUS-запроса; шлюзу их адреса знать не нужно вовсе.

## 2. Перед началом --- контрольный список

1. Шлюз установлен (см. `README_RU.md`, раздел *Установка*). После установки у вас есть:
   - сама программа: `/opt/mbusgw-t2r/sbin/mbusgw-t2r`
   - файл настроек: `/opt/mbusgw-t2r/etc/modbus-t2r_settings.conf`
2. Вы знаете, **к какому последовательному порту** подключено устройство. В Linux это файл
   вида `/dev/ttyS0`, `/dev/ttyUSB0` или `/dev/ttyXRUSB0`. Если не уверены --- выдерните и
   вставьте USB-адаптер и выполните `dmesg | tail`: имя порта будет в выводе.
3. Вы знаете **параметры линии** устройства: скорость, число бит данных, чётность, стоп-биты.
   Они написаны в паспорте устройства. Самый распространённый набор: `9600, 8, N, 1`.
4. Ваш пользователь имеет право открыть порт. Простейшая проверка: `ls -l /dev/ttyUSB0` ---
   если группа `dialout`, добавьте себя в неё: `sudo usermod -a -G dialout $USER` (после
   этого перезайдите в систему), либо просто запускайте шлюз через `sudo`.

## 3. Файл настроек, строка за строкой

В файле два раздела: `serials` (последовательные линии) и `listeners` (TCP-порты). Откройте
его любым редактором:

```
$ sudo nano /opt/mbusgw-t2r/etc/modbus-t2r_settings.conf
```

Минимальный рабочий пример:

```
serials = (
	{	device = "/dev/ttyUSB0";
		chars  = "9600, 8, N, 1";
		iotmo  = 1000;
	}
);

listeners = (
	{	bind   = "TCP:0.0.0.0:502";
		target = "/dev/ttyUSB0";
		connlm = 8;
	}
);
```

Читается так: *«открой порт /dev/ttyUSB0 на 9600-8-N-1, жди ответа до 1000 мс; слушай
TCP-клиентов на всех сетевых интерфейсах, порт 502, и пересылай их на этот порт»*.

### 3.1. Раздел `serials` --- по записи на каждый последовательный порт

| Ключ | Обязателен? | Что означает | Допустимые значения |
|------|-------------|--------------|---------------------|
| `device` | **да** | Файл последовательного порта | например `/dev/ttyUSB0` |
| `chars` | **да** | Параметры линии: `скорость, биты данных, чётность, стоп-биты` | скорость 50..4000000; биты данных 5..8; чётность `N` (нет), `E` (чётная), `O` (нечётная); стоп-биты 1..2 |
| `iotmo` | нет | Сколько ждать ответа устройства, в **миллисекундах**. По умолчанию 1000. Берите **с запасом** относительно самого медленного устройства на линии: ответ, пришедший позже `iotmo`, теряется | любое положительное число |
| `lategd` | нет | После неудачного запроса (нет ответа, битый ответ) шлюз ещё столько **миллисекунд** слушает линию и выбрасывает всё, что пришло (`%T2R-W-LATEANS`): опоздавший ответ не должен уйти следующему запросу. Время тратится только после сбоя: запрос к неработающему устройству занимает `iotmo` + `lategd`. По умолчанию `iotmo` / 4; `0` --- только пауза в 3,5 символа, как до X.00-13ECO08 | 0..60000 |
| `rs485` | нет | `1` --- просить ядро управлять направлением RS-485 (только для портов, которые это умеют) | `0` или `1` |
| `ts_enabled` | нет | `1` --- включить встроенное псевдоустройство меток времени (см. раздел 6) | `0` или `1` |
| `ts_unit` | нет | Адрес ведомого, на который отвечает псевдоустройство | 1..247, по умолчанию 135 |
| `ts_fncode` | нет | Код функции, на который оно отвечает | по умолчанию 4 |
| `ts_base_reg0` | нет | Номер первого регистра метки времени | по умолчанию 135 |

Если запись неправильная, шлюз **пропускает её и говорит почему** --- с допустимым
диапазоном прямо в сообщении, например:

```
%T2R-E-SERRANGE, [serial #00:</dev/ttyUSB0>] --- speed (baud) 31 is out of range [50..4000000]
```

Номер записи (`#00`) считается с нуля, в порядке следования записей в файле.

**USB-адаптеры: переподключать можно.** С X.00-13ECO09 шлюз переживает переподключение
USB-адаптера (или сброс хаба):

- шлюз замечает, что адаптер пропал (`%T2R-E-DEVLOST`) --- даже когда никто не опрашивает
  устройство --- и сразу закрывает порт;
- раз в секунду он пытается открыть порт снова по его имени; пока адаптера нет, клиенты получают
  исключение **10** (`GATEWAY_PATH_UNAVAILABLE`), а не 4;
- когда адаптер вернулся, в журнале появляется `%T2R-S-DEVREADY` и работа продолжается, перезапуск не нужен;
- если адаптера нет при старте шлюза, его TCP-порт всё равно открывается (`%T2R-W-DEVABSENT`), а
  порт заработает, когда адаптер появится.

**Используйте постоянное имя.** Ядро раздаёт номера `ttyUSB0`, `ttyUSB1`, ... в порядке появления
адаптеров, и после переподключения тот же адаптер может получить другой номер. Поэтому пишите в
`device` (и в `target` листенера) постоянное имя:

- имя по USB-разъёму: `ls -l /dev/serial/by-path/` --- например
  `/dev/serial/by-path/platform-xhci-hcd.0-usb-0:1.1:1.0-port0` (у 4-портового FT4232H порты
  отличаются частью `:1.0`, `:1.1`, `:1.2`, `:1.3`);
- или своё имя через правило udev, например `/dev/rs485-1`:
  `SUBSYSTEM=="tty", ENV{ID_PATH}=="platform-xhci-hcd.0-usb-0:1.1:1.0", SYMLINK+="rs485-1"`
  в `/etc/udev/rules.d/99-rs485.rules` (значения смотрите в `udevadm info /dev/ttyUSB0`).

### 3.2. Раздел `listeners` --- по записи на каждый TCP-порт

| Ключ | Обязателен? | Что означает | Допустимые значения |
|------|-------------|--------------|---------------------|
| `bind` | **да** | Где слушать: `TCP:<IP-адрес>:<порт>` | порт 1..65535; `0.0.0.0` = все интерфейсы; UDP не поддерживается |
| `target` | **да** | На какой порт пересылать --- должен **дословно** совпадать с `device` из `serials` | |
| `connlm` | нет | Сколько TCP-клиентов может быть подключено к этому порту **одновременно**; лишний сразу отключается (`CONNLIMIT`). По умолчанию 32 | 1..512 |
| `idletmo` | нет | Клиент, который ничего не присылает столько **секунд**, отключается (`IDLETMO`). По умолчанию 60 | 1..86400 |
| `mode` | нет | Что делает слушатель: `"MODBUS"` --- шлюз MODBUS TCP в RTU, `"RAW"` --- прозрачный поток октетов (см. 3.3). Заглавные или строчные буквы --- не важно. Любое другое слово --- ошибка (`LSNBADMODE`). По умолчанию `"MODBUS"` | `"MODBUS"`, `"RAW"` |
| `takeover` | нет | **Только для `RAW`.** `1`: новый клиент вытесняет текущего (`RAWKICK`). `0`: пока подключён другой клиент, новый отклоняется (`RAWBUSY`). В режиме `MODBUS` этот ключ --- ошибка (`LSNRAWOPT`). По умолчанию 1 | 0..1 |
| `iotmo` | нет | Зарезервирован, пока не используется | |

В режиме `RAW` два умолчания другие: `connlm` может быть только 1, а `idletmo` равен 86400 (не 60).

Замечания для самого начала:

- Порт **502** --- стандартный порт MODBUS TCP, но в Linux порты ниже 1024 требуют прав root.
  Не хотите работать под root --- возьмите, например, `5502` и укажите его в клиенте.
- Несколько `MODBUS`-слушателей могут разделять один `target` --- шлюз выстроит их запросы в очередь.
  `RAW`-слушателю последовательный порт нужен целиком (см. 3.3).

### 3.3. Режим RAW (прозрачный)

В режиме `MODBUS` шлюз понимает MODBUS. В режиме `RAW` --- **нет**. Он просто переносит октеты
от TCP-клиента в последовательную линию и из линии клиенту. Ничего не меняет. Это «виртуальный
COM-порт по сети».

Типичный случай: на ПК с Windows есть программа для старого прибора. Программе нужен COM-порт.
Вы ставите на ПК программу «COM через TCP» (она создаёт виртуальный COM-порт и соединяет его со
шлюзом по TCP). Программа думает, что работает с настоящим COM-портом. Прибор может говорить на
**любом** последовательном протоколе, не только на MODBUS.

```
 [Программа на ПК] --- виртуальный COM --- TCP ---> [mbusgw-t2r, режим RAW] --- линия ---> [Прибор]
```

Пример настроек:

```
listeners = (
	{ bind = "TCP:0.0.0.0:4001"; mode = "RAW"; target = "/dev/ttyUSB1"; }
);
serials = (
	{ device = "/dev/ttyUSB1"; chars = "19200, 8, E, 1"; flow = "NONE"; iotmo = 1000; }
);
```

Правила режима RAW:

- **Один клиент за раз.** `connlm` может быть только 1.
- **Новый клиент вытесняет старого** (`takeover = 1`, по умолчанию). Старое соединение
  закрывается, линию получает новый. В журнале будет `RAWKICK`. При `takeover = 0` старый
  клиент остаётся, а новому отказывают (`RAWBUSY`).
- **Последовательный порт --- только для этого слушателя.** Ни один другой слушатель, MODBUS
  или RAW, не может брать тот же `target` (`LSNRAWSHR`; порядок записей не важен).
  MODBUS-слушатели по-прежнему могут делить порт между собой.
- **Скорость и чётность берутся из шлюза.** Они заданы в записи `serials`. Если программа на ПК
  ставит у своего виртуального COM-порта другую скорость, в линию это **не** передаётся.
  Задайте верный `chars` в записи `serials`.
- **Долгое молчание --- это нормально.** `idletmo` по умолчанию --- 86400 секунд (сутки). Только
  после этого шлюз закроет клиента. А вот мёртвого клиента (ПК упал, кабель оборван) находит
  TCP keepalive, и его отбрасывают примерно за 1 минуту (30 секунд тишины, потом 3 пробы с шагом 10 секунд).
- **Меток времени нет.** Псевдоустройство `ts_*` (глава 6) в режиме RAW не работает.
- В начале сессии старые октеты в буферах последовательного порта выбрасываются.

Замечание для обоих режимов: начиная с X.00-14 вход последовательного порта «бинарно чистый».
Порт больше не превращает CR в LF и не обрезает 8-й бит. Раньше октет `0x0D` мог прийти как
`0x0A` на порту с настройками по умолчанию.

## 4. Запуск шлюза

Вручную, в терминале (сообщения идут прямо на экран):

```
$ /opt/mbusgw-t2r/sbin/mbusgw-t2r /settings=/opt/mbusgw-t2r/etc/modbus-t2r_settings.conf
```

Полезные опции:

| Опция | Смысл |
|-------|-------|
| `/settings=<файл>` | Файл настроек (см. выше) |
| `/trace` | Подробная трассировка: каждый запрос и ответ печатается в hex. Бесценно при первом запуске |
| `/logfile=<файл>` | Писать журнал в файл вместо экрана |
| `/logsize=<октет>` | Ротировать файл журнала при превышении этого размера |

Здоровый запуск выглядит так (сокращённо):

```
%T2R-I-REVISNF, Rev: T2R X.00-06/aarch64(built at ...) (REV: 00.06.00)
%T2R-I-DEVADDED, Added device #00 [</dev/ttyUSB0>, Chars: <9600, 8, N, 1>, ...] --- added
%T2R-I-LSNADDED, Added listener #00 [Target: </dev/ttyUSB0>, Net: <TCP:0.0.0.0:502>, ...] --- added
%T2R-S-DEVREADY, Device </dev/ttyUSB0> [9600 baud, answer tmo: 1000 msec, t3.5: 4010 usec] --- is ready
%T2R-S-LSNRRDY, [#3] Listener 0.0.0.0:502 [Target: </dev/ttyUSB0>] --- is ready
```

Важнее всего две строки: **DEVREADY** (порт открыт) и **LSNRRDY** (TCP-порт слушает). Видите
обе --- шлюз работает.

Остановка: один раз `Ctrl+C` и секунда ожидания. Переключить трассировку у *уже работающего*
шлюза без перезапуска: `kill -USR1 <pid>`.

### 4.1. Первая проверка с mbpoll

`mbpoll` --- маленький свободный MODBUS-клиент (`sudo apt install mbpoll`). Читаем 3 регистра
хранения с устройства с адресом 1:

```
$ mbpoll -a 1 -r 1 -c 3 -1 127.0.0.1 -p 502
```

Если вернулись числа --- всё работает, из конца в конец.

### 4.2. На OpenWrt

На роутер с OpenWrt ставьте пакет для своей платы со страницы Releases (архитектура — строка
`DISTRIB_ARCH` в `/etc/openwrt_release`): `.ipk` для OpenWrt 24.10, `.apk` для OpenWrt 25.12.
Пакету больше ничего не нужно, сеть роутеру не нужна:

```
# opkg install ./mbusgw-t2r_0.13.9-*_mipsel_24kc.ipk
# apk add --allow-untrusted ./mbusgw-t2r_0.13.9-*_mipsel_24kc.apk
```

Файлы лежат не там, где на Debian: программа — `/usr/sbin/mbusgw-t2r`, файл настроек —
`/etc/mbusgw-t2r/modbus-t2r_settings.conf`. После установки служба выключена. Настройте файл
настроек, затем включите службу и запустите её:

```
# uci set mbusgw-t2r.main.enabled=1 && uci commit mbusgw-t2r
# /etc/init.d/mbusgw-t2r start
# logread -e mbusgw-t2r
```

Последняя команда показывает сообщения шлюза (они идут в системный журнал). Адаптеру USB-serial
нужен модуль ядра: `kmod-usb-serial-ftdi`, `kmod-usb-serial-ch341` или `kmod-usb-serial-cp210x` —
по микросхеме адаптера.

## 5. Как читать журнал

Каждое важное событие печатается строкой с **кодом сообщения**:

```
%T2R-E-CRC16ERR, [#4:</dev/ttyUSB0>] RTU CRC16 check error (received: 0x1234, calculated: 0xABCD)
 ^   ^  ^
 |   |  +-- код: ищите его в таблице раздела 7
 |   +----- серьёзность: S=успех, I=информация, W=предупреждение, E=ошибка, F=фатально
 +--------- подсистема (у этой программы всегда T2R)
```

`[#4:</dev/ttyUSB0>]` означает: файловый дескриптор #4, вот этот последовательный порт.

## 6. Псевдоустройство меток времени

Шлюз умеет отвечать *сам* --- не трогая линию --- на запрос чтения, посланный на специальный
адрес ведомого. Ответ --- текущее время машины, на которой работает шлюз. Так SCADA может
читать точное время по обычному MODBUS.

При `ts_enabled = 1; ts_unit = 135; ts_fncode = 4; ts_base_reg0 = 135;` запрос «прочитай N
входных регистров начиная со 135-го у ведомого 135» возвращает:

| Запрошено регистров | Что получаете |
|---------------------|---------------|
| 4 | секунды эпохи UNIX, 64 бита, старшее 16-битное слово первым: R0=биты 63..48, R1=47..32, R2=31..16, R3=15..0 |
| 8 | + наносекунды, упакованные так же в R4..R7 |
| 9 | + R8 = смещение местного часового пояса, в **знаковых минутах** (например, Москва = +180) |

Секунды собираются как `(R0<<48)|(R1<<32)|(R2<<16)|R3`.

Любое другое число регистров в TS-запросе получает MODBUS-исключение
`ILLEGAL_DATA_ADDRESS` --- это сделано намеренно.

## 7. Траблшутинг --- симптом, причина, действие

**Золотое правило: запустите с `/trace` и читайте журнал. Шлюз всегда говорит, что именно
ему не нравится.**

| Вы видите | Что это значит | Что делать |
|-----------|----------------|------------|
| `%T2R-E-DEVOPNERR, Cannot open the device </dev/ttyUSB0>, errno: 2` | errno 2 = файла нет: адаптер выдернут или имя неверное | `dmesg \| tail` после втыкания адаптера; поправьте `device` в настройках. С X.00-13ECO09 TCP-порт всё равно открывается (`DEVABSENT`), устройство пробуется раз в секунду |
| `%T2R-E-DEVLOST, [...] tcflush(), errno: 5 --- the device is lost, it will be reopened every 1000 msec` (или `writev()`, `read()`, `hangup`) | USB-адаптер пропал: выдернут, сброс хаба, просадка питания; клиенты получают исключение 10 | ничего, если он вернётся: следом будет `DEVREADY`. Если нет: `dmesg \| tail`; проверьте кабель и питание; если он вернулся под другим номером `ttyUSB` --- используйте постоянное имя (раздел 3.1) |
| `%T2R-W-DEVABSENT, Device <...> is absent --- it will be opened every 1000 msec ...` | При старте последовательный порт не открылся (почему --- в строке выше); его TCP-порт работает и отвечает исключением 10 | подключите адаптер --- следом будет `DEVREADY`; или поправьте `device` в настройках |
| Клиент получает исключение `0x0A` (10) | Последовательного порта этого TCP-порта нет или он пропал (см. `DEVLOST`, `DEVABSENT`) | см. `DEVLOST` выше |
| то же, `errno: 13` | Нет прав доступа | запустите под `sudo` или добавьте себя в группу `dialout` |
| то же, `errno: 16` | Порт занят: его держит другая программа | найдите её: `sudo fuser /dev/ttyUSB0`; остановите |
| `%T2R-E-NOANSWER, [...] Did not get an answer in 1000 msec` | Запрос ушёл, ответа нет | 1) неверный адрес ведомого в запросе клиента; 2) перепутаны провода (поменяйте A/B у RS-485); 3) не та скорость/чётность --- перепроверьте `chars`; 4) устройство просто выключено |
| `%T2R-E-CRC16ERR, [...] (received: X, calculated: Y)` | Байты приходят, но повреждённые | 1) `chars` не совпадает с устройством (самое частое!); 2) помехи на линии --- проверьте землю, терминаторы, длину кабеля; 3) два мастера на одной линии |
| `CRC16ERR` на части запросов после перезагрузки или переподключения адаптера; пропадает, если порт перед этим открывала любая другая программа (`stty raw`, pyserial) | Шлюз старше X.00-13ECO07 оставлял у свежего порта замену CR на NL (`icrnl`): байт 0x0D в ответе превращался в 0x0A | обновитесь до X.00-13ECO07 или новее; для старого шлюза: `ExecStartPre=/bin/stty -F /dev/ttyUSB0 raw` (на каждый порт) в юните |
| `%T2R-E-BADFRAME, [...] N octets, allowed [5..256]` | Что-то пришло, но это не осмысленный MODBUS-кадр | обычно те же причины, что у CRC16ERR; при 400+ октетах мусора --- на линии чужое, не-MODBUS устройство |
| `%T2R-W-FRAMETMO, [...] Frame is not completed in ...` | Ответ начался, но не завершился вовремя | очень медленное или зависшее устройство; увеличьте `iotmo`; проверьте кабель |
| `CRC16ERR`, `BADFRAME` или `FRAMETMO` время от времени, только на USB-адаптере (FTDI); прямой `mbpoll` на том же порту работает без ошибок | Адаптер FTDI отдаёт ответ кусками, раз в 16 мс (его `latency_timer`). С X.00-10 шлюз дожидается всего ответа для обычных функций (01-06, 15, 16, 23), но остальные функции по-прежнему обрезаются | поставьте `latency_timer` в 1 мс --- заодно каждый ответ станет быстрее: `sudo cp /opt/mbusgw-t2r/share/doc/mbusgw-t2r/99-ftdi-latency.rules /etc/udev/rules.d/`, затем `sudo udevadm control --reload && sudo udevadm trigger --subsystem-match=usb-serial`; проверка: `cat /sys/bus/usb-serial/devices/ttyUSB0/latency_timer` должна напечатать `1` |
| `%T2R-W-LATEANS, [...] N octets have arrived after the failed exchange (a late answer?) --- dropped` после `NOANSWER` | Устройство ответило, но позже `iotmo`; ответ выброшен | увеличьте `iotmo` этого порта: берите его с запасом относительно самого медленного устройства на линии |
| `%T2R-W-ECHOMISM, [...] Echo of the write request: address A, value/quantity V (REQ: ...) --- mismatch` | Ответ на запись (функции 5, 6, 15, 16) --- не эхо этого запроса: обычно это опоздавший ответ на предыдущий запрос; клиент получает исключение 4 | увеличьте `iotmo` (см. LATEANS); если устройство быстрое --- на линии два мастера; если это происходит на **каждой** записи в одно устройство --- устройство отвечает на запись не эхом, как требует спецификация MODBUS (например, возвращает записанное и ограниченное значение): запись выполнена, но считается неудачной --- сообщите нам модель устройства |
| `%T2R-W-EXCRPT, [...] Report exception 4 (SERVER_DEVICE_FAILURE) ...` | Шлюз сообщил TCP-клиенту «на последовательной стороне сбой» | смотрите *предыдущую* строку журнала --- в ней настоящая причина (NOANSWER, CRC16ERR, ...) |
| `%T2R-W-CONNLIMIT, [...] --- the listener has reached its connection limit (N) --- the connection is rejected` | К порту уже подключено `connlm` клиентов | если все они настоящие --- увеличьте `connlm` этого слушателя; иначе найдите, кто держит соединения: `ss -tn` |
| `%T2R-W-IDLETMO, [...] No activity for the past N seconds (idletmo) --- close the connection` | Клиент ничего не присылал `idletmo` секунд | нормально для клиента, который опрашивает редко --- он переподключится; чтобы держать соединение, увеличьте `idletmo` этого слушателя |
| `%T2R-E-LSNRAWSHR, [listener #NN] --- target <...> is used by the listener on port N too, ...` | RAW-слушатель хочет последовательный порт, который занят другим слушателем | дайте RAW-слушателю отдельный порт, либо переведите другого слушателя на другой порт; либо сделайте RAW-слушатель MODBUS-слушателем |
| `%T2R-W-RAWBUSY, [...] --- the raw listener is busy and <takeover> is off --- the connection is rejected` | К RAW-порту уже подключён клиент, а `takeover = 0` | это нормально. Отключите первого клиента или поставьте `takeover = 1` |
| `%T2R-E-TTYPOLLEV, [...] poll()->N, .revents: XXXX --- the serial line has failed` | Последовательный порт отказал во время RAW-сессии (вынули USB-адаптер) | переподключите адаптер, смотрите `dmesg \| tail`; клиент подключится заново, и сессия начнётся снова |
| `%T2R-E-TXDRAINTMO, [...] --- the request has not been transmitted in N msec` | USB-адаптер принял запрос, но не передал его в линию; запрос получает исключение 4 | адаптер или его USB-связь зависли: `dmesg \| tail`; переподключите адаптер или перезагрузите плату. С X.00-13ECO01 линия из-за этого не блокируется: следующий запрос пробует снова |
| `%T2R-E-DEVLOCKERR` / `DEVBUSY` на каждом запросе одного порта, остальные порты в порядке | Линию держит другой запрос, который не заканчивается | обновитесь до X.00-13ECO01 или новее (старый шлюз мог навсегда зависнуть в драйвере порта). Перед перезапуском сохраните, что делает зависший поток: `for t in /proc/$(pidof mbusgw-t2r)/task/*; do echo $t $(cat $t/wchan); done` |
| `%T2R-E-SESSFAIL, [...] --- cannot start a session thread, pthread_create()->11` | Слишком много TCP-клиентов сразу: каждому нужен поток, а systemd ограничивает сервис (`TasksMax`, на маленькой плате 578) | найдите, кто держит столько соединений (`ss -tn`); если все они настоящие --- поднимите предел: `TasksMax=2048` в разделе `[Service]` юнита, затем `systemctl daemon-reload` |
| `%T2R-E-LSNRERR, Listener 0.0.0.0:502 --- bind() error, errno: 98` | errno 98 = TCP-порт уже занят | работает второй экземпляр шлюза, или порт держит другая программа: `sudo ss -tlnp \| grep 502` |
| то же, `errno: 13` | Порты ниже 1024 требуют root | запустите под `sudo` или возьмите порт >= 1024 (например 5502) |
| `%T2R-E-SERRANGE, [serial #NN:...] --- ... out of range [a..b]` (or `LSNRANGE`) | Значение в настройках вне допустимого диапазона | исправьте значение; допустимый диапазон написан прямо в сообщении |
| `%T2R-E-NOSERIALS, No serials have been defined!` | Ни одна запись `serials` не прошла проверку | читайте строки ошибок выше --- каждая отброшенная запись объясняет причину |
| Клиент подключается, но каждый ответ --- исключение `0x04` | См. EXCRPT выше | беда на последовательной стороне; `/trace` и читайте журнал снизу вверх |
| Всё выглядит хорошо, но данные неверные/сдвинутые | Путаница порядка байт на стороне клиента | регистры MODBUS --- 16-битные слова big-endian; проверьте, как ваш клиент собирает 32/64-битные значения |

## 8. Если ничего не помогло

Соберите и приложите к вопросу:

1. полный журнал запуска с `/trace` (от `REVISNF` до первой ошибки),
2. ваш файл настроек,
3. вывод `ls -l <устройство>` и `dmesg | tail -20`,
4. точную модель RTU-устройства и его паспортные параметры линии.

С этими четырьмя вещами проблема почти всегда видна с первого взгляда.
