# Шлюз MODBUS TCP в RTU

[![ci](https://github.com/napilab/mbus-gw-t2r/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/napilab/mbus-gw-t2r/actions/workflows/ci.yml)

*[English version: README.md](README.md)*

Ещё один шлюз MODBUS TCP → RTU (ограниченное издание специально для команд LAB240 и NaPiLab).

###	NaPi World
Проект разрабатывается и сопровождается командой NaPi Lab, основное тестирование идёт на
промышленных одноплатных компьютерах NaPi на процессорах Rockchip.

####	Платы NaPi
Если вы ищете надёжную аппаратную платформу для промышленной эксплуатации транспортного
программного обеспечения MODBUS, посмотрите линейку плат NaPi:

Добро пожаловать в NaPi World (https://github.com/napilab/napi-boards)!

Сейчас доступны:

- NAPI2 — RK3568J, RS-485 на плате, Armbian
- NAPI-C — RK3308, компактная, промышленного исполнения


###	Введение
Простой в использовании шлюз TCP → RTU для протокола MODBUS. Подходит (и не только) для:

 - развития общих навыков программирования
 - навыков программирования ввода-вывода на портах RS-232 и RS-485
 - базовой проверки работоспособности устройств с поддержкой MODBUS
 - построения двунаправленных шлюзов TCP → RTU и RTU → TCP (пока не реализовано)
 - прозрачной передачи последовательного ввода-вывода поверх TCP (доступно: режим RAW слушателя)

###	Основные возможности и достоинства
  - обслуживает несколько устройств MODBUS на одной линии RS-485
  - обслуживает одну линию RS-485 с нескольких TCP-портов
  - поддержка специфики сигналов RS-232 и RS-485
  - один процесс с многопоточной архитектурой для высокой производительности
  - согласование доступа нескольких TCP-клиентов к одной последовательной шине или устройству
  - устойчивая обработка ошибок, распознавание мусора на линии и приёмы восстановления

###	Когда выбрать mbusgw-t2r вместо mbusd

Этот проект — альтернатива известному шлюзу [mbusd](https://github.com/3cky/mbusd) для случая,
когда нужна высокая эффективность при меньшей ресурсоёмкости. Оба переводят MODBUS TCP в RTU;
различия, которые имеют значение на практике:

  - **Дисциплина последовательной линии.** Конец кадра определяется по честному критерию
    тишины t3.5 с межкадровым интервалом строго по спецификации — шина RTU работает на
    физическом максимуме, никакие фиксированные паузы на запрос не вставляются.
  - **Модель ожидания.** Всё ожидание построено на `poll()`, без тикающих в фоне таймеров:
    простаивающий шлюз потребляет практически ноль процессорного времени, что важно на малой
    промышленной плате со скромным энергобюджетом.
  - **Диагностика.** Каждая ошибка — кодированное, пригодное для grep сообщение с конкретной
    причиной (значения CRC, `errno`, допустимый диапазон): поиск неисправности превращается в
    чтение, а не в гадание.
  - **Дополнительно.** Несколько TCP-портов на одну линию, несколько линий в одном процессе,
    встроенное псевдоустройство меток времени, управление направлением RS-485 средствами
    ядра — и всё это в бинарнике около 100 КБ, которому кроме libc ничего не нужно.

Если mbusd вас устраивает — оставайтесь на нём. Если вы выжимаете максимум из загруженной
линии RS-485 на небольшой машине или устали гадать, почему запрос не прошёл, — этот шлюз для
вас.

###	Надёжность, ресурсоёмкость и производительность

**Ни одна ошибка не проскакивает.** Каждый кадр RTU, пришедший с линии, проверяется прежде чем
ему поверят: сверяется трейлер CRC16, длина кадра проверяется по разумному диапазону
[5..256] октетов, конец кадра определяется по честному критерию тишины t3.5 из спецификации
MODBUS over Serial Line, а ответ сверяется с запросом по адресу ведомого и коду функции.
Длинам, заявленным «с провода», доверия нет. Мусор на линии — даже сотни октетов — отвергается
чистым MODBUS-исключением в адрес TCP-клиента, линия сбрасывается, и следующий же запрос
обслуживается нормально.

**Ни одна ошибка не молчит.** Каждый отказ порождает кодированное сообщение журнала
(`%T2R-E-CRC16ERR`, `%T2R-E-NOANSWER`, ...), которое называет причину: полученное и
вычисленное значения CRC, `errno` отказавшего системного вызова, допустимый диапазон
неверно заданного параметра. Журнал спроектирован так, чтобы искать в нём по коду и чтобы
поиск неисправности был чтением, а не гаданием — см. руководство пользователя, глава 7.

**Малый след.** Один процесс; зависимостей времени выполнения помимо libc нет. Бинарник
около 100 КБ; набор StarLet и libconfig линкуются статически. Нигде нет циклов
активного ожидания: всё ожидание построено на `poll()`, поэтому простаивающий шлюз почти не
потребляет процессор. Поток существует только на *активную* TCP-сессию и освобождается сразу
после отключения клиента (утечек потоков и памяти нет — подтверждено прилагаемым стендом и
сборками под ASan/UBSan). Благодаря этому шлюз комфортно живёт на малых промышленных
одноплатных компьютерах линейки NaPi (RK3308, RK3568J) — и на чём угодно крупнее.

**Линия работает на физическом максимуме.** Сквозная задержка определяется самой
последовательной линией; сторона TCP добавляет микросекунды (установлен `TCP_NODELAY`, ответы
пишутся одним куском). Одновременные TCP-клиенты сериализуются на линию мьютексом, поэтому
шина RTU утилизируется впритык — с обязательным по спецификации межкадровым интервалом t3.5 и
ничем сверх того, — при этом каждый клиент получает свой ответ в порядке поступления.
Несколько независимых линий обслуживаются параллельно, каждая на своей полной скорости.

###	Установка

Шлюз зависит от двух пакетов: **libconfig** (разбор файла настроек, берётся из дистрибутива;
линкуется статически, `-DT2R_STATIC_LIBCONFIG=OFF` — с разделяемой) и
**StarLet** (набор UTILITY$ROUTINES, ставится из исходников как пакет CMake). Полная
последовательность от чистой системы до работающего шлюза:

####	Шаг 1. Установить средства сборки

```
$ sudo apt install build-essential cmake pkg-config libconfig-dev
```
(в дистрибутивах на основе RPM: `sudo dnf install gcc make cmake pkgconf libconfig-devel`)

####	Шаг 2. Установить пакет StarLet

```
$ git clone https://gitlab.com/SysMan-One/utility_routines
$ cd utility_routines
$ mkdir build && cd build
$ cmake ../ -DCMAKE_BUILD_TYPE=Release
$ make -s
$ sudo cmake --install .
```

Пакет ставится в `/usr/local`: библиотека `libstarlet`, публичные заголовки и конфигурация
пакета CMake (после этого становится доступен `find_package(StarLet)`). Чтобы установить в
другой префикс, используйте `sudo cmake --install . --prefix /opt/starlet`, а на шаге 3
передайте шлюзу `-DCMAKE_PREFIX_PATH=/opt/starlet`.

####	Шаг 3. Собрать шлюз

```
$ git clone <URL репозитория>
$ cd mbus-gw-t2r
$ mkdir build && cd build
$ cmake ../ -DCMAKE_BUILD_TYPE=Release
$ make -s
```

Типы сборки: `Release` (эксплуатация), `Debug` (символы, трассировка), `Asan` (санитайзеры
адресов и неопределённого поведения, для разработки).

####	Сборка с musl (OpenWrt, Alpine, встраиваемые образы)

Шлюз собирается и работает и с библиотекой **musl** — это обычный случай для образов на основе
OpenWrt и Alpine на промышленных платах. В комплект входит toolchain-файл:

```
$ cmake ../ -DCMAKE_TOOLCHAIN_FILE=../cmake/musl.cmake -DCMAKE_BUILD_TYPE=Release \
	-DCMAKE_PREFIX_PATH=<префикс musl>
$ make -s
```

Зависимости (StarLet и libconfig) тоже должны быть собраны под musl и установлены в этот
префикс; укажите `PKG_CONFIG_LIBDIR` на его `lib/pkgconfig`, чтобы подхватился musl-вариант
libconfig, а не системный.

Одна особенность musl, которую берёт на себя toolchain-файл: musl поставляет собственные
заголовки, но не заголовки ядра (`linux/serial.h`, `asm/ioctls.h`), поэтому каталоги заголовков
ядра добавляются через `-idirafter` — так заголовки musl всегда выигрывают, а `/usr/include`
просматривается только ради того, чего в musl нет. Обычный `-I` отравил бы сборку заголовками
glibc.

####	Шаг 4. Установить шлюз

```
$ sudo make install
```

Что куда попадает:

| Что | Куда |
|-----|------|
| Бинарник `mbusgw-t2r` и утилита `mbus-ctl` | `/opt/mbusgw-t2r/sbin/` (.deb добавляет симлинк `/usr/sbin/mbus-ctl`) |
| Файлы конфигурации | `/opt/mbusgw-t2r/etc/` |
| Документация и эталонные копии конфигов | `/opt/mbusgw-t2r/share/doc/mbusgw-t2r/` |

Файлы конфигурации ставятся **только если их нет**: повторный `make install` (обновление)
никогда не затирает настроенную рабочую конфигурацию — такие файлы отмечаются в выводе как
`Keeping the existing ...`.

Префикс по умолчанию — `/opt/mbusgw-t2r`: самодостаточное дерево, которое удаляется целиком.
Чтобы поставить в другое место, задайте префикс на шаге 3:
`cmake ../ -DCMAKE_INSTALL_PREFIX=/usr/local ...` — тогда бинарник попадёт в `/usr/local/sbin/`,
файлы конфигурации — в `/usr/local/etc/mbusgw-t2r/`, документация — в
`/usr/local/share/doc/mbusgw-t2r/`.

**USB-адаптеры FTDI** (FT232/FT2232/FT4232): поставьте правило udev, которое выставляет им
`latency_timer` в 1 мс --- ответы приходят быстрее и никогда не обрезаются:
`sudo cp /opt/mbusgw-t2r/share/doc/mbusgw-t2r/99-ftdi-latency.rules /etc/udev/rules.d/` (подробности
в самом файле правила и в руководстве пользователя, раздел *Траблшутинг*).

####	Шаг 5. Настроить и запустить

```
$ sudo vi /opt/mbusgw-t2r/etc/modbus-t2r_settings.conf
$ /opt/mbusgw-t2r/sbin/mbusgw-t2r /settings=/opt/mbusgw-t2r/etc/modbus-t2r_settings.conf
```

Формат файла настроек — в разделе *Правила запуска и настройки* ниже.

####	Деинсталляция

```
$ cd mbus-gw-t2r/build
$ sudo make uninstall
```

Удаляется всё, что поставил `make install`, кроме файлов конфигурации в `/opt/mbusgw-t2r/etc/` —
настроенная рабочая конфигурация переживает деинсталляцию всегда.

####	Готовые пакеты (GitHub Releases)

К каждому релизному тегу на GitHub (`v0.13.5` и новее) прикладываются пакеты `.deb` для amd64 и
arm64: https://github.com/napilab/mbus-gw-t2r/releases. Они собраны на Debian 12 и требуют только
glibc 2.34 или новее (проверены на Debian 12, Debian 13 и Ubuntu 24.04); libconfig и StarLet
слинкованы статически. Пакет ставит шлюз в `/opt/mbusgw-t2r/` и службу systemd
`mbusgw-t2r.service` — она ставится **выключенной**: сначала настройте файл настроек:

```
$ sudo apt install ./mbusgw-t2r_1.1.0-1_arm64.deb
$ sudo nano /opt/mbusgw-t2r/etc/modbus-t2r_settings.conf
$ sudo systemctl enable --now mbusgw-t2r
```

Файлы настроек — conffiles: при обновлении настроенные сохраняются. Сборку делает
`.github/workflows/release.yml`; локально тот же пакет собирается так:
`cmake ../ -DCMAKE_BUILD_TYPE=Release -DT2R_SYSTEMD_UNIT=ON && make -s && cpack -G DEB`.

Пакеты `.deb` для **mipsel** и **mips64el** (`v0.13.6` и новее) — кросс-сборка для Debian 12
(в Debian 13 портов MIPS нет); ставятся так же.

####	Пакеты для OpenWrt (GitHub Releases)

Начиная с `v0.13.6` в релизе есть и пакеты OpenWrt для `mips_24kc` (ath79 и другие MIPS-платы
big-endian), `mipsel_24kc` (ramips: MT7621, MT7628/MT7688), `aarch64_cortex-a53`,
`arm_cortex-a7`, `arm_cortex-a7_neon-vfpv4` (ipq40xx, sunxi) и `x86_64`: `.ipk` для OpenWrt 24.10
и `.apk` для OpenWrt 25.12. Архитектура пакетов вашей платы — строка `DISTRIB_ARCH` в
`/etc/openwrt_release`. libconfig и StarLet слинкованы статически: у пакета нет зависимостей,
сеть роутеру для установки не нужна:

```
# opkg install ./mbusgw-t2r_1.1.0-*_mipsel_24kc.ipk			# OpenWrt 24.10
# apk add --allow-untrusted ./mbusgw-t2r_1.1.0-*_mipsel_24kc.apk	# OpenWrt 25.12
```

Пакет ставит шлюз в `/usr/sbin/mbusgw-t2r`, настройки — в `/etc/mbusgw-t2r/`, службу procd —
`/etc/init.d/mbusgw-t2r`. Служба **выключена**, пока вы не настроите файл настроек и не включите
её; её сообщения идут в системный журнал:

```
# vi /etc/mbusgw-t2r/modbus-t2r_settings.conf
# uci set mbusgw-t2r.main.enabled=1 && uci commit mbusgw-t2r
# /etc/init.d/mbusgw-t2r start
# logread -e mbusgw-t2r
```

Пакеты собирает официальный OpenWrt SDK из фида `openwrt/` этого репозитория (`mbusgw-t2r` и
вспомогательные `starlet` и `libconfig-static`, только для сборки); пакеты `x86_64` и `mips_24kc` перед релизом
ставятся и запускаются в образах OpenWrt. Собрать своим SDK:
`echo "src-link mbusgw <это дерево>/openwrt" >> feeds.conf`,
`./scripts/feeds update mbusgw && ./scripts/feeds install mbusgw-t2r`,
`make package/mbusgw-t2r/compile`.

####	Проверка скачанного

В релизе, сделанном после 10-NOV-2026, есть `SHA256SUMS.minisig` — подпись
[minisign](https://jedisct1.github.io/minisign/) файла `SHA256SUMS`: одна подпись на все пакеты и
архив исходников релиза. Открытый ключ лежит в `minisign.pub` этого репозитория:

    RWQl4NAqFsHKkNoHkS52WSZSk+2kb+e58DWYpoi/jVFa6TqOTAm3Ph14

Положите скачанные файлы рядом с `SHA256SUMS` и `SHA256SUMS.minisig` и выполните:

    minisign -Vm SHA256SUMS -P RWQl4NAqFsHKkNoHkS52WSZSk+2kb+e58DWYpoi/jVFa6TqOTAm3Ph14
    sha256sum -c --ignore-missing SHA256SUMS

Первая команда должна сказать `Signature and comment signature verified`, вторая — `OK` для
каждого файла. Иначе файл не тот, что выпущен: не ставьте его. В более ранних релизах есть только
`SHA256SUMS`.

####	Автоматические тесты (GitHub Actions)

Workflow `.github/workflows/ci.yml` (значок в начале файла) при каждом push и pull request собирает
StarLet и шлюз на amd64 и arm64 и прогоняет тесты, которым не нужно железо:
`tests/issues_test.py all` и `tests/ctl_test.py` (пара pty и имитатор ведомого RTU).

####	Автоматическая сборка (GitLab CI)

Файл `.gitlab-ci.yml` собирает шлюз при каждом push в репозиторий на GitLab. Он делает те же шаги,
что описаны выше, в Docker-образе `gcc`:

1. ставит `cmake`, `pkg-config` и `libconfig-dev`;
2. клонирует StarLet из `https://gitlab.com/SysMan-One/utility_routines.git`, собирает его и ставит
   в `/usr/local` (адрес задан переменной `STARLET_REPO` — замените его, чтобы брать StarLet из зеркала);
3. собирает шлюз в каталоге `build/` (Debug).

Задание только проверяет, что код компилируется: шлюз оно не устанавливает и бинарник не сохраняет.
Если задание упало на шаге StarLet, проверьте, что репозиторий StarLet доступен с раннера.

###	Правила запуска и настройки

####	Быстрый старт

##### Общий формат командной строки
```
./build/mbusgw-t2r <опции> --settings=<файл-настроек-сети-и-портов>
```

##### Пример:

```
./build/mbusgw-t2r --trace --settings=modbus-t2r-settins.conf
```

##### Опции командной строки

| Опция			|  Описание
| ------		| ------------------------------------------------------------
| trace			| Включить подробную диагностику. Полезно при отладке и поиске неисправностей.
| logfile=\<fspec\>	| Задать файл для вывода журнала
| logsize=\<число\>	| Ограничить размер файла журнала
| settings=\<fspec\>	| Задать файл конфигурации сети и последовательных устройств
| control=\<путь\>	| Сокет управления для `mbus-ctl` (по умолчанию `/var/run/mbusgw-t2r.sock`); `NONE` выключает канал управления
| check			| Проверить файл настроек и выйти: код возврата 0, если всё хорошо (`%T2R-S-CHECKOK`)


##### Параметры файла настроек
Смотрите пример файла настроек как справочник параметров и правил конфигурирования, либо
руководство пользователя (глава 3) — там описан каждый ключ с допустимым диапазоном значений.

Раздел `listeners` — одна запись на TCP-порт:

| Ключ | Обязателен | Смысл | Значения |
|------|------------|-------|----------|
| `bind` | да | Протокол, адрес и порт для приёма соединений | `"TCP:0.0.0.0:502"` (UDP не поддерживается) |
| `target` | да | Последовательное устройство (из раздела `serials`), куда передаются запросы | `"/dev/ttyUSB0"` |
| `connlm` | нет | Сколько TCP-клиентов может быть подключено к этому порту **одновременно**; лишний сразу отключается (`%T2R-W-CONNLIMIT`) | 1..512, по умолчанию 32 |
| `idletmo` | нет | Клиент, который ничего не присылает столько **секунд**, отключается (`%T2R-W-IDLETMO`); клиент, опрашивающий редко, просто переподключится | 1..86400, по умолчанию 60 |
| `mode` | нет | `"MODBUS"` --- шлюз MODBUS TCP в RTU; `"RAW"` --- прозрачный поток октетов (см. *Режим RAW (прозрачный)* ниже). Регистр не важен; любое другое значение отбрасывает запись (`%T2R-E-LSNBADMODE`) | `"MODBUS"` (по умолчанию), `"RAW"` |
| `takeover` | нет | **Только RAW.** `1`: новый клиент вытесняет текущего (`%T2R-W-RAWKICK`); `0`: пока клиент подключён, новый отклоняется (`%T2R-W-RAWBUSY`). В режиме MODBUS ключ --- ошибка (`%T2R-E-LSNRAWOPT`) | 0..1, по умолчанию 1 |
| `iotmo` | нет | Зарезервирован, пока не используется | |

Значение `connlm`/`idletmo` вне диапазона отбрасывает всю запись слушателя (`%T2R-E-LSNOPTRNG`).
В режиме RAW `connlm` может быть только 1, а `idletmo` по умолчанию равен 86400 (не 60).
Каждый одновременный клиент занимает один поток: при большом числе клиентов учитывайте лимит
`TasksMax` юнита systemd (см. в руководстве пользователя *Траблшутинг*, `SESSFAIL`).

```
listeners = (
	{bind = "TCP:0.0.0.0:502"; target = "/dev/ttyUSB0"; connlm = 16; idletmo = 60;}
);
```

##### Режим RAW (прозрачный)
При `mode = "RAW"` слушатель вообще не говорит на MODBUS: он пересылает октеты **как есть**
между одним TCP-клиентом и последовательной линией, в обе стороны. Это виртуальный COM-порт
поверх TCP: программа на ПК с Windows (через драйвер виртуального COM-порта, который передаёт
байты по TCP) видит удалённый последовательный порт как локальный. Работает с **любым**
последовательным протоколом, не только с MODBUS.

```
listeners = (
	{bind = "TCP:0.0.0.0:4001"; mode = "RAW"; target = "/dev/ttyUSB1";}
);
serials = (
	{device = "/dev/ttyUSB1"; chars = "19200, 8, E, 1"; flow = "NONE"; iotmo = 1000;}
);
```

Ограничения и правила:

 - Один клиент за раз (`connlm` может быть только 1). По умолчанию новый клиент **вытесняет**
   старого: старое соединение закрывается (`RAWKICK`). При `takeover = 0` новый клиент отклоняется (`RAWBUSY`).
 - Последовательную линию RAW-слушателя нельзя использовать в другом слушателе, ни в MODBUS, ни
   в RAW (`%T2R-E-LSNRAWSHR`). MODBUS-слушатели по-прежнему могут делить линию между собой.
 - Скорость, чётность и стоп-биты берутся из записи `serials` шлюза. То, что удалённая программа
   задаёт у своего виртуального COM-порта, **не** передаётся.
 - `idletmo` по умолчанию --- 86400 секунд. Клиент, который умер молча (сбой, обрыв кабеля),
   отбрасывается TCP keepalive примерно за 1 минуту (30 с простоя + 3 пробы по 10 с).
 - Псевдоустройство меток времени (`ts_*`) в режиме RAW не используется.

**Программа в Linux как клиент.** Драйвер псевдопоследовательного порта `serial2net` (NaPi Lab,
X.00-08ECO1 и новее) создаёт `/dev/ser2net00`, `/dev/ser2net01` и так далее и переносит всё, что туда записано, как есть на
TCP-партнёра. Направьте партнёра на RAW-слушатель (`p_ser2net_peer="127.0.0.1:4001"`), и любая
программа, которой нужен последовательный порт (`mbpoll -m rtu`, `minicom`, `pyserial`), работает с
удалённой линией как с местным портом. Скорость по-прежнему берётся из записи `serials` шлюза.
Проверено: 1 МиБ в каждую сторону блоками с CRC32 (без потерь), четыре порта одновременно с
`mbpoll`, 115200.

Начиная с X.00-14 вход последовательной линии бинарно чистый в **обоих** режимах (без замены CR/NL,
без обрезания 8-го бита): раньше октет 0x0D мог прийти как 0x0A на порту с настройками по умолчанию.

###	Мониторинг и управление: mbus-ctl

`mbus-ctl` — маленькая утилита, она ставится рядом со шлюзом. Она спрашивает **работающий** шлюз,
что он делает, и отдаёт ему несколько команд. Утилита говорит со шлюзом через локальный файл-сокет
(по умолчанию `/var/run/mbusgw-t2r.sock`, опция шлюза `/CONTROL=`): в сеть ничего не открывается.
Кому можно управлять, решают права файла сокета: `0660`, владелец и группа шлюза (для шлюза,
запущенного системой, — `sudo mbus-ctl ...`).

| Команда | Что делает |
|---------|------------|
| `mbus-ctl SHOW CONNECTIONS [/CONTINUOUS[=<сек>]]` | TCP-клиенты по слушателям: адрес, время подключения, запросы, ответы, ошибки и октеты |
| `mbus-ctl SHOW LINES` (или `SERIALS`) | Последовательные линии: устройство, параметры, таймауты, OPEN/ABSENT, сколько клиентов ими пользуется |
| `mbus-ctl SHOW GATEWAY` (или `GW`) | Версия, PID, время работы, файл настроек, слушатели и их счётчики |
| `mbus-ctl RESET CONNECTIONS <id \| a.b.c.d \| a.b.c.d:порт>` | Отключить TCP-клиента(ов); id — столбец `Id` из SHOW CONNECTIONS |
| `mbus-ctl RESET CONNECTIONS /ALL` | Отключить всех TCP-клиентов |
| `mbus-ctl RESTART GATEWAY [/WAIT=<сек> \| /NOWAIT]` | Проверить файл настроек и перезапустить шлюз (он перечитает настройки, заново откроет слушателей и линии) |
| `mbus-ctl HELP` | Список команд |

Каждая команда понимает `/SOCKET=<путь>` (или `--socket=<путь>`) — для шлюза с другим `/CONTROL=`.
Слова можно сокращать: `sho conn /cont`, `sho gw`, `sho ser`, `reset conn 7`,
`restart gw`. `/CONTINUOUS` перерисовывает экран каждые 2 секунды (или `<сек>`) до `Ctrl-C` и ждёт
шлюз, пока его нет (перезапуск).

```
$ sudo mbus-ctl sho conn			# .deb: /usr/sbin/mbus-ctl; 'make install': /opt/mbusgw-t2r/sbin/mbus-ctl
Connections of the MODBUS gateway at 07-NOV-2026 00:07:44

Listener #0  127.0.0.1:45459  MODBUS -> /dev/ttyUSB0  UP, 2 of 8 connection(s), accepted 2, rejected 0
      Id   Sd  Client                 Connected             Duration    Requests   Answers  Errors    Bytes in   Bytes out
       1    8  127.0.0.1:44770        07-NOV-2026 00:07:44  00:00:00           7         7       0          84          91
       2    9  127.0.0.1:44772        07-NOV-2026 00:07:44  00:00:00           3         3       0          36          33

Listener #1  127.0.0.1:39779  RAW -> /dev/ttyUSB1  UP, 1 of 1 connection(s), accepted 1, rejected 0
      Id   Sd  Client                 Connected             Duration    Requests   Answers  Errors     To line   From line
       3   10  127.0.0.1:57778        07-NOV-2026 00:07:44  00:00:00           -         -       -           5           5

Total: 3 connection(s)
```

`Sd` — это `[#n]` в строках журнала этого клиента. `Errors` считает ответы с исключением MODBUS
и запросы, на которых соединение оборвалось.

**RESTART GATEWAY** не боится опечатки: сначала шлюз запускает `mbusgw-t2r /settings=<файл> /check`
(отдельный процесс, работающий шлюз не трогается); если файл плохой, перезапуск отклоняется,
`mbus-ctl` показывает строки с ошибками, а шлюз работает дальше как был (`%T2R-E-CTLCHKFAIL`). Если
файл хороший, шлюз отвечает, отпускает клиентов (до 10 с), закрывает слушателей и линии и запускает
**сам себя** заново с той же командной строкой — тот же PID, так что systemd и procd этого даже не
замечают. Клиенты просто переподключаются. `mbus-ctl` ждёт, пока шлюз снова ответит
(`%T2R-S-CTLBACK`). `systemctl reload mbusgw-t2r` делает то же самое. Перезапуск запускает тот файл
программы, который работает сейчас: после обновления пакета перезапускайте службу (.deb делает это сам).

Канал управления говорит на маленьком двоичном протоколе — StarLet AVProto TLV; текстового вида у
него нет, на текстовую строку шлюз не отвечает. Один запрос на соединение: клиент шлёт один PDU,
шлюз отвечает одним PDU и закрывает соединение:

```
PDU     = HEADER TLV TLV ...
HEADER  = magic[8] "MBUSCTL"  u_len  u_csr  u_seq          20 октетов, числа в сетевом порядке
TLV     = [type:4 | tag:12]   len    value                 числа WORD/LONGWORD/QWORD, тексты BBLOCK

запрос:   u_csr = команда: 1 SHOW GATEWAY, 2 SHOW LINES, 3 SHOW CONNECTIONS,
                  4 RESET CONNECTIONS (ALL | ID | ADDR [PORT]), 5 RESTART GATEWAY
ответ:    u_csr = статус (младший бит установлен — успех), тот же u_seq, записи:
          REC=LISTENER LSN ADDR PORT MODE TARGET STATE CONNLM IDLETMO SESSIONS ACCEPTED REJECTED
          REC=CONN     ID SD LSN MODE ADDR PORT SINCE RESET NREQ NANS NERR NRX NTX
          ...          REASON — почему запрос не выполнен
```

Коды команд и тегов — в `src/t2r_ctlproto.h`, клиент — `mbus-ctl` (`src/mbus_ctl.c`);
`tests/ctl_test.py` говорит со шлюзом из Python через `struct` — короткий пример другого клиента.

Запросы: `SHOW GATEWAY`, `SHOW LINES`, `SHOW CONNECTIONS`, `RESET CONNECTIONS <id|адрес|адрес:порт|ALL>`,
`RESTART GATEWAY`, `HELP` (полные слова, регистр любой). Несколько шлюзов на одной машине: дайте
каждому свой `/CONTROL=<путь>`; второй шлюз на занятом пути работает без канала управления
(`%T2R-W-CTLBUSY`) и никогда не забирает сокет первого.

## Стиль кода

Исходники написаны в едином стиле, и заплатка должна ему следовать:

 - **Форматирование:** скобки Whitesmiths (скобка на отдельной строке, с отступом вместе с телом;
   скобки тела рутины не сдвигаются). Только табуляции (8 колонок), без пробелов. Строки до 192 колонок.
 - **Префиксы:** `g_` глобальные, `l_` локальные, `s_` статические (рутины тоже), `a_` параметры
   рутин, `m_` битовые маски, `v_` битовые поля. Переменные объявляются в начале блока, по типам
   (типы из `stdint.h`).
 - **Имена:** `$` разделяет слова в макросах и константах (`T2R$K_BAUD_MAX`, `T2R$K_SETTLE_MSEC`).
   Структуры объявляются с суффиксом тега `_t`.
 - **Каждый файл** начинается с `__MODULE__`, `__IDENT__` и `__REV__` (`X.00-14ECO02` --- это
   `00.14.02`), затем идёт заголовок: подсистема, аннотация, история изменений, а для
   каждой рутины --- входы, выходы, неявные входы и выходы и возвращаемое значение.
 - **Сообщения** выводятся только макросами библиотеки StarLet (`$LOG_FAO`, `$PUTMSG_FAO` и
   обёртка проекта над ними) с кодами из каталога сообщений, но не через `printf`, `perror` или
   `syslog`. Рутина возвращает статус (младший бит --- успех), результаты отдаются через выходные
   параметры, а при ошибке библиотеки Си в журнал пишется `errno`. Тесты и текст `/HELP` ---
   исключение.
 - **Документация** пишется на двух языках, русском и английском, для самых маленьких, с
   строкой в разделе поиска неисправностей для каждого кода сообщения.
